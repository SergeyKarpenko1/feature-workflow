# feature-workflow — дизайн универсального плагина

**Дата:** 2026-11-02
**Статус:** draft
**Репозиторий:** `github.com/SergeyKarpenko1/feature-workflow`, лицензия MIT

## 1. Зачем

Агент пишет код быстро, но человек ему не доверяет и проверяет всё сам: читает длинный план, прогоняет проверки, смотрит логи. Узкое место переезжает с кода на внимание человека.

`feature-workflow` проводит фичу или багфикс через цепочку фаз. Каждая фаза пишет короткий артефакт, после неё стоит **детерминированный гейт** (скрипт, не модель), на ключевых переходах — **судья** (модель другого класса или другого вендора), а человек решает только в фиксированных точках: что делаем (enrich), как (дизайн), что считать «готово» (тест-план), спорные эскалации и финальное ревью. Человек получает отчёт «прошло / не прошло» с цифрами вместо проверки с нуля.

Основа — подход «research → plan → implement с гейтами между фазами». Процесс уже отработан на реальном проекте в виде локальной версии под один репозиторий; этот плагин — его универсальная версия.

## 2. Цели, не-цели, анти-цели

**Цели:**
- Работает в любом проекте после одной настройки `/feature-init`.
- Работает в двух агентах с первой версии: Claude Code и Codex CLI.
- Ядро не зависит от вендора; адаптеры тонкие.
- Судья может быть моделью другого вендора (код пишет один, проверяет другой).
- Установка одной-двумя командами из GitHub для каждого агента.
- README на русском, ниже — полная английская версия.

**Не-цели (v1):**
- Antigravity CLI, Gemini CLI — не нужны.
- Cursor, Aider, OpenCode и прочие — позже.
- Мутационное тестирование, CRAP, DAST — как гейты не входят; можно подключить через команды конфига.
- Веб-интерфейс, сервер, телеметрия.

**Анти-цели (провал, даже если работает):**
- В репозитории есть хоть что-то из проекта, на котором процесс родился: имена, пути, домен, сервисы.
- Процесс заставляет человека читать больше, чем без него.
- Плагин обещает защиту секретов, которой в конкретном агенте нет.
- Агент сам меняет дизайн, когда судья нашёл архитектурную ошибку.

## 4. Устройство репозитория

```
feature-workflow/
  core/
    skills/
      feature/SKILL.md          # процесс: фазы, точки остановки, правила
      feature-init/SKILL.md     # настройка проекта
    scripts/
      feature_gate.py           # гейты, triage, снимки (stdlib, Python ≥ 3.11)
      guard.py                  # охранник секретов, --format claude|codex
      judge.py                  # запуск судьи по команде из конфига, разбор вердикта
    judges/
      design.md  arch.md        # промпты судей (не привязаны к вендору)
      verdict.schema.json
    templates/{ru,en}/          # STATE.md, 01-enrich.md … 09-report.md
    tests/                      # pytest на гейты, охранник, judge.py
  adapters/
    claude/   .claude-plugin/plugin.json, agents/, hooks/hooks.json
    codex/    манифест плагина, hooks, agents/*.toml
  .claude-plugin/marketplace.json  # репозиторий = маркетплейс Claude Code
  examples/
    config.example.toml
    verify/chat_api_eval.sh     # пример команды Verify для LLM-фич
  docs/  vendors.md  config.md  how-it-works.md
  README.md  LICENSE
```

Ядро одно; адаптер ссылается на него, а не копирует. Если формат установки требует файлов внутри адаптера, сборочный скрипт `scripts/build_adapters.py` раскладывает ядро в каждый адаптер, и CI проверяет, что разложенное совпадает с ядром.

## 5. Ядро

### 5.1 Процесс
Фазы, артефакты, точки остановки — как в исходной версии:
Enrich → Research → Triage → Design → Acceptance → Plan → Code → QA-check → Deploy → Verify → Review; короткий цикл Enrich → Research → Triage → Acceptance → Code → Verify → Review.

Правила, переносимые без изменений: гейт после каждой фазы (код 0 / 1 / 2), лимит 3 провала подряд, эскалация «чинить код / вернуться в дизайн» решается человеком, утверждённый тест-план нельзя ослабить, план без кода и ≤ 150 строк, `code-start` фиксирует уже грязные файлы, агент не коммитит и не пушит, разрешение на правку файлов человек даёт явно на ветку (`edits_allowed:` в `STATE.md`), три сессии на задачу с разными моделями.

**Первый запуск и карточка задачи.** Если в проекте нет `.feature/config.toml`, `/feature` сначала запускает `/feature-init` (§7) и только потом идёт в Enrich. Имя ветки выдаётся на старте. Если `tracker.task_card = true`, после прохождения гейта Enrich скилл выдаёт в чат (на языке `language`) название и описание задачи для трекера — проблема, что делаем, откат, критерии приёмки, — собранные из `01-enrich.md`. В трекер плагин ничего не пишет.

### 5.2 Гейт
`feature_gate.py` берёт всё проектное из конфига (§6): команды тестов и линтера, baseline упавших тестов, правила triage, базовую ветку, язык заголовков. Ни одного зашитого пути проекта. Заголовки разделов — из таблицы `ru`/`en`; гейт принимает язык из конфига.

### 5.3 Судьи
Промпты `judges/design.md`, `judges/arch.md` описывают проверки в общем виде: решение отвечает на задачу, затронутые инварианты разобраны, нет выдуманных значений (каждое — найти в репо), есть откат, контракты объявлены, diff соответствует дизайну, слои и правила из базы знаний соблюдены. Проектные правила судья берёт из базы знаний, которую указывает конфиг (`CLAUDE.md`, `AGENTS.md`, `docs/`, ADR).

Запуск — два способа, выбор в конфиге:
- `native` — сабагент своего агента (модель другого класса);
- `command` — внешний CLI, в том числе другого вендора, по шаблону из конфига; `judge.py` подставляет промпт и схему, вызывает команду, достаёт вердикт (`structured_output` / файл `-o`), проверяет его по `verdict.schema.json`.

Правило: судья другого класса или вендора, чем автор того, что он проверяет.

### 5.4 Охранник секретов
`guard.py` — один скрипт для двух агентов. Читает JSON со stdin, проверяет команду или путь по шаблонам из конфига (по умолчанию: dotenv-файлы, ключи, `printenv`/`env`, `/proc/*/environ`, `docker inspect|logs`, рекурсивный поиск по корню). Ответ — в формате агента: `--format claude|codex` → exit 2 + причина в stderr.

Запись в защищённые файлы (`.feature/config.toml`, `*.approved.md`, `preexisting.txt`) проверяется только у инструментов записи с `file_path`; команды Bash (`echo >`, `sed -i`, `tee`) не перехватываются. Хук — страховка, а не граница безопасности. README прямо говорит, что настоящий запрет — правила доступа самого агента, и `/feature-init` выдаёт их готовым блоком для вставки.

### 5.5 Шаблоны
`templates/ru` и `templates/en`, одинаковая структура, подсказки в `<!-- -->` (гейт считает такой раздел пустым).

## 6. Конфиг проекта

`.feature/config.toml` в корне проекта (TOML — stdlib `tomllib`, без зависимостей). Пишет `/feature-init`, человек подтверждает. Поля:

- `language = "ru" | "en"`, `base_branch = "main"`
- `[commands]` `lint`, `test` (+ `test_summary_regex`), `test_baseline` (файл с известными падениями или пусто)
- `[triage]` — правила `name`, `paths` (glob), `reason`; порог файлов и слоёв (`layers` — glob → слой)
- `[domains]` — `core` / `supporting` / `generic` → glob, задаёт глубину ревью и модель Code
- `[knowledge]` — пути базы знаний для судей
- `[secrets]` — шаблоны путей и команд для охранника
- `[deploy]` — `start`, `health`, `stop` (или пусто, если проект не надо поднимать)
- `[verify]` — именованные команды проверки, на которые ссылается тест-план (`verify:<имя>`)
- `[models]` — для своего агента: `decide` (enrich, design, acceptance, code в core), `check` (research, plan, qa-check, verify)
- `[judges]` — `mode = native|command`, шаблоны команд для `design` и `arch`
- `agent` — какой агент у пользователя (`claude`, `codex` или другое имя); информационное поле, его пишет `/feature-init`
- `[tracker]` — `kind` (имя трекера задач: `jira`, `linear`, любое другое или `none`), `task_card` (`true` — после Enrich выдавать название и описание задачи для трекера); раздел необязателен, по умолчанию `none` и `false`

Тест-план ссылается на проверки из `[verify]`, а не на «ответ API» и «трейс» — это частный случай. Пример для LLM-фич — `examples/verify/chat_api_eval.sh`.

## 7. `/feature-init`

1. Определяет агента по окружению; если не удалось — спрашивает (Claude Code, Codex CLI или другой). Для «другого» ядро работает, но хука охранника и готовых скиллов нет — init говорит об этом прямо.
2. Изучает проект: менеджер пакетов, команды тестов и линтера, CI, Dockerfile/compose, файлы инструкций и `docs/`, где лежат миграции, публичные схемы, конфиги деплоя, файлы секретов.
3. Показывает найденное по разделам конфига и задаёт вопросы только о том, чего не нашёл (типы доменов, команды проверки, что считать опасными зонами). Отдельно спрашивает, какой трекер задач использует человек (Jira, Linear, GitHub Issues, другой или никакого); если трекер есть — нужна ли карточка задачи (название и описание) перед каждой фичей.
4. Прогоняет тесты один раз и предлагает записать текущие падения как baseline.
5. Пишет `.feature/config.toml` после явного «да».
6. Выдаёт для своего агента готовый блок правил запрета секретов — пользователь вставляет сам.
7. Проверка: `feature_gate.py check-config`.

## 10. «Ничего от исходного проекта»

- Код и тексты пишутся заново по этому документу, файлы локальной версии не копируются.
- Перед каждой публикацией — проверка по списку запрещённых слов (имена компании и сервисов, пути, доменные термины исходного проекта). **Сам список хранится вне репозитория** — иначе он и есть утечка; скрипт проверки принимает путь к нему аргументом.
- Примеры (`examples/`) — на вымышленном проекте.
- История git чистая с первого коммита: если утечка найдена после коммита, переписать историю до публикации.

## 11. Проверка

- `core/tests/` — pytest на гейты, triage по конфигу, охранник в обоих форматах, `judge.py` с подставным CLI.
- `claude plugin validate` — локально перед публикацией (CLI в CI-раннере недоступен); в CI — pytest, проверка сборки адаптеров и JSON-манифестов.
- Сквозная проверка на учебном проекте в `examples/sample-project/`: init → короткий цикл до Verify, плюс Codex как внешний судья (`codex exec -s read-only`).
- **Условие выпуска v1 (решение автора):** сквозная проверка пройдена в **Claude Code и Codex CLI**.
- Пилот: одна реальная задача в стороннем проекте автора через плагин (не через локальную версию).

## 12. Публикация и отношение к локальной версии

- Локальная версия в исходном проекте остаётся и развивается отдельно (вариант 2). Перенос улучшений — вручную, по решению автора.
- Создание репозитория на GitHub и `git push` — только после проверки §10 и отдельной команды автора «публикуй».

## 13. Решения, принятые без обсуждения (проверить)

- Конфиг в TOML, не YAML: `tomllib` в stdlib, Python ≥ 3.11.
- Ядро + сборка в адаптеры с проверкой в CI вместо симлинков (симлинки ломаются при установке плагинов).
- Codex: судья по умолчанию `command` с `codex exec -s read-only` — у сабагентов нет своей песочницы.
- Тест-план ссылается на именованные команды `[verify]` вместо `auto:response` / `auto:trace`.
- Модели по умолчанию — табл. §8; пользователь меняет в конфиге.

- **Исходная локальная версия — функциональная спецификация.** Исполнитель читает её (скилл, гейт, шаблоны, судьи, спеку процесса), чтобы перенести поведение: разделы артефактов, проверки гейтов, правила эскалации. Код и тексты пишет заново; ни одна строка, путь, имя или доменный пример оттуда не попадает в репозиторий. Проверка §10 — после каждой задачи, не только перед публикацией.
- **Verify в общем виде.** Команда из `[verify]` сообщает результат кодом выхода (0 — прошло) и по желанию печатает в stdout одну строку JSON с метриками `{"<metric>": <число>}`. Критерий тест-плана: `| id | что | verify:<имя> | порог | повторы |`; порог — либо `pass`, либо выражение над метрикой (`hit_rate >= 0.9`). Гейт `verify` запускает команду `повторы` раз и сравнивает. Снимок «до» (запуск тех же команд до первой правки, без флагов фичи) остаётся в ядре и включается полем `## Baseline`. `questions.tsv` и контрольный вопрос — только в примере для LLM-фич (`examples/verify/`), не в ядре.
- **Вспомогательные скиллы встроены.** Интервью фазы Enrich и дамп сигнатур фазы Research описаны прямо в `feature/SKILL.md` (по одному разделу), внешних скиллов плагин не требует. Коммит в Review — «как вы привыкли», без привязки к скиллу.
- **Защита правил от правки агентом.** `guard.py` запрещает инструменты записи для `.feature/config.toml`, `*.approved.md` и `preexisting.txt` в обоих агентах; меняет их только человек или подкоманды гейта.
- **Плагин пишет в репозиторий пользователя только** `.feature/config.toml` и папки фич. Если что-то нельзя поставить плагином, v1 этого не обещает: для Codex судья по умолчанию `command` через `codex exec`, отдельные файлы агентов не нужны.

- **Счётчик провалов подряд живёт в фиче.** Строка `failures: <phase>=<n>` в `STATE.md` фичи; гейт увеличивает её при провале, сбрасывает при успехе, при `n ≥ 3` возвращает код 2 (эскалация).
- **Глобы — свой матчер.** `fnmatch` не подходит: `**/` в нём требует хотя бы одного `/`, и файлы в корне проекта не совпадают. Все глобы (triage, layers, domains, охранник) идут через один `glob_match`.
- **Команды конфига ограничены по времени.** `[commands] timeout_sec` (по умолчанию 600) действует на тесты, команды `[verify]` и health-проверку deploy.
- **Deploy — две подкоманды гейта.** `deploy-up` запускает `start` и ждёт `health`, `deploy-down` запускает `stop`; при пустом `[deploy]` обе пропускаются.
- **Снимок «до» включается разделом `## Baseline`** (`да`/`нет`) в `04-acceptance`; при `да` гейт `verify` требует `runs/before.json`.

- **Карточка задачи — текст в чат, один формат.** Плагин не обращается к трекеру (ни API, ни MCP) и не знает его формата; формат один для всех трекеров, настраиваемые шаблоны добавляются, когда понадобятся.

## 14. Оставлено исполнителю

- Точная схема `config.toml` и сообщения `check-config`.
- Формат `verdict.schema.json` (база — `{"verdict","findings":[{"severity","where","why","design_level"}]}`).
- Как `/feature-init` определяет агента.
- Структура `examples/sample-project/`.
